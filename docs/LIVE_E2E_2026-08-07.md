## 2. What happened — stage 02 as committed FAILS; run completed via a documented diagnostic bypass

`02_extract.py`'s `client.messages.parse(output_format=FrdIngestionSpec)`
fails **deterministically** with:

```
400 invalid_request_error: The compiled grammar is too large, which would
cause performance issues. Simplify your tool schemas or reduce the number
of strict tools.   (request_id req_011CdnctxUpRRFN2qr61yXia)
```

The SDK (0.120.2) transmits the Pydantic schema via the modern
`output_config.format` json_schema path; the API compiles that schema into a
server-side grammar, and `FrdIngestionSpec`'s grammar exceeds the compiler's
complexity limit. **No repo code was modified.** Diagnostic probes (400s are
rejected pre-generation and unbilled):

| Probe | Result |
|---|---|
| A. Trivial 1-field schema via same path | ACCEPTED (key/model/plumbing fine) |
| B. Full `FrdIngestionSpec` schema | 400 grammar too large (fast reject) |
| C. Full schema, **all descriptions stripped** | 400 grammar too large — the limit is **structural**, not prose |
| D. `Feed` sub-model alone | No verdict in 120 s (compilation ground past read-timeout) — even one level down strains the compiler |

Schema stats: 11,227 chars, 38 properties, 25 `anyOf` nullable unions
(Pydantic `Optional[...]`), 4 `$defs`, `additionalProperties: false`
throughout (the wire form of `extra="forbid"`).

**Bypass used to complete the run** (scratch-only script,
`data/live_run_logs/02b_extract_bypass.log`; zero repo-code changes): same
model, same `SYSTEM_PROMPT`, and the **same schema including all field
descriptions** sent as prompt text, response validated client-side with
`FrdIngestionSpec.model_validate_json` (`extra="forbid"`) — the exact
posture the repo's removed Gemini path used. Output written to the scratch
extractions dir; stages 03/04 then ran **unmodified**.

## 4D. Defect catalogue

1. **D1 — BLOCKER: structured-outputs grammar limit kills stage 02 as
   committed.** *Symptom:* deterministic 400 "compiled grammar is too
   large" from `messages.parse(output_format=FrdIngestionSpec)`; the
   pipeline has never actually run live from this repo. *Root cause:*
   structural schema complexity (38 properties, 25 nullable `anyOf` unions,
   `additionalProperties:false` everywhere) exceeds the API grammar
   compiler's limit; probe C proves descriptions are irrelevant; probe D
   shows even the `Feed` sub-model strains it. *Proposed fix (options):*
   (a) schema-in-prompt + client-side `extra="forbid"` validation +
   completeness gate — today's bypass; identical machinery existed in the
   removed Gemini path and measured 0 hallucinations / 45-45 strict here;
   (b) restructure the schema to shrink the grammar (required-with-null
   instead of `Optional` unions, flatten `TableTarget`); (c) split into
   top-level + per-feed calls; (d) raise the limit question with Anthropic.
   Recommend (a) short-term with (b) explored before scale-up.
2. **D2 — Zero-removal attribution groups never auto-clear**
   (`notebooks/04_sttm_render.py:683-688`). *Symptom:* live run ends
   PASS_WITH_FLAGS while the mock ends PASS, despite the live attribution
   being dictionary-correct. *Root cause:* `resolve_attribution` clears
   attribution ambiguities only `if resolutions:` (i.e., only when it
   removed something); an extraction already matching the
   dictionary-consistent assignment yields zero removals, so its gated flag
   survives — **a better extraction produces a worse final status.**
   *Proposed fix:* run the dictionary consistency check over surviving
   attribution ambiguities and clear any whose candidate set equals the
   dictionary-confirmed set; keep the human gate when the dictionary is
   inconclusive.
3. **R3 — RISK: single-call extraction with a 16k output ceiling.**
   *Symptom (quantified, this run):* 3,273/16,000 output tokens (20.5%) for
   a 3-feed demo FRD; ≈ 700–800 tokens/feed ⇒ ceiling at ~15–20 feeds;
   truncation raises immediately (correct fail-loud, but no fallback).
   *Proposed fix:* streaming + larger `max_tokens` (128k available when
   streaming) as the cheap first step; per-feed chunked extraction if
   real FRDs exceed that.
4. **D4 — MINOR: frequency/SLA duplication.** Live places near-identical
   verbatim text in both `frequency` and `load_windows_sla` for all three
   feeds. Grounded and harmless; a reviewer would trim. *Fix (optional):*
   sharpen the two field descriptions to disjoint scopes.
5. **N5 — Demo-consistency note (not a defect):** a live demo shows **1**
   gated review item, not the 3 the mock-driven demo script produces, and
   (until D2 is fixed) a PASS_WITH_FLAGS final tile instead of PASS.
   Rehearse against the live shape or fix D2 first.

**Does anything trace to the Task-1/previous anonymization scrubs
(3a3aa8f, a485258)? No — explicitly ruled out on both axes.**
(1) The D1 grammar 400 is structural: the descriptions-stripped schema
fails identically, and the scrubs only ever changed description strings.
(2) Extraction quality on the scrubbed prompt shows no degradation
signal: 0/50 hallucinated identifiers, 45/45 strict + 30/30 advisory
grounding, attribution matching the dictionary ground truth, and eval
byte-equal to the curated baseline (94.1%, same 194 deliberate misses).
The anonymized example tokens steered format only; every identifier in the
output came verbatim from the document.

# Post-fix re-run (same day)

The morning run's defects were fixed and the full pipeline was re-proven
live on the **committed** path (no bypass), insulated under the
`_live_e2e_20260807b` suffix.

## What changed

- **D1 fixed** — the bypass transport was promoted to the committed live
  path: new `src/frdsttm/live_extraction.py` (+ `notebooks/_live_extraction.py`
  shim, per the repo's shim pattern) renders the full `FrdIngestionSpec`
  JSON schema — field descriptions included — into the user prompt, makes a
  plain **streaming** `messages.stream()` call, and validates the response
  client-side with `extra="forbid"`. `messages.parse(output_format=...)` is
  gone from `02_extract.py`. A validation failure raises immediately naming
  every failed field; **deliberately no re-ask/repair loop** (a schema error
  is a deterministic output-shape error, and a silent re-ask would blur the
  quality signal).
- **R3 mitigated** — the call streams, and `max_tokens` default raised
  16,000 → 64,000 (still the `max_tokens` widget/env knob; model stays the
  `model` knob, default `claude-opus-4-8` — no new literals in logic). New
  headroom supports ~75–90 feeds at the measured ~700–800 output tokens/feed.
- **D2 fixed** — `resolve_attribution` now confirm-and-clears an
  attribution ambiguity whose candidate feeds exactly equal the
  dictionary-confirmed set (zero-removal case), each cleared individually;
  dictionary-inconclusive ambiguities keep their human gate. Covered by
  `tests/test_render_attribution.py`, which lifts the committed function
  from `04_sttm_render.py` via AST so the tests exercise the real code.
- **Tests** — suite grew 41 → **54** (10 live-transport tests against a
  stubbed streaming client incl. config passthrough, fence tolerance,
  validation-failure raise, unusable-stop-reason handling; 3 attribution
  tests: zero-removal clears, inconclusive stays gated, removal-path
  regression guard).
- **Mock-gate baseline: unchanged.** Post-fix mock run reproduces the
  baseline byte-for-byte (extraction + both reports identical; contracts
  differ only in `generated_date`): PASS, 94.1%, 3288 cells, same 5
  attribution resolutions. No baseline regeneration was needed — the mock
  path is untouched by the transport change, and the D2 confirmation pass
  does not fire on the mock's spread-across-all-feeds shape.
